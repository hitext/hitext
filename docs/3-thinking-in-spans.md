# Thinking in Spans

HiText does not provide a separate high-level primitive for every kind of text view.

The previous guide built one diagnostic view step by step. This chapter generalizes the relationships used there and applies them to a different domain.

Search excerpts, diagnostics, syntax highlighting, folding, generated summaries, redaction, focused logs, and progressive disclosure may look like unrelated features. In practice, they are usually built from a small number of recurring relationships between spans over one source document.

The important skill is therefore not memorizing span functions. It is learning to identify:

* which facts already exist as spans;
* which spans should be derived from them;
* which spans affect the visible result;
* which spans exist only as intermediate products;
* and when the resulting view should be materialized.

Once a task is expressed in those terms, the corresponding HiText pipeline is usually straightforward.

## Start with facts, not presentation

Suppose a transcript analyzer identifies an action item:

```js
{
    start: 120,
    end: 131,
    data: {
        assignee: 'Mina',
        due: 'Friday'
    }
}
```

The span describes a fact about the source document:

> This action item is stated in the source range `[120, 131)`.

It does not yet decide how that fact should appear.

The same action item might be represented as:

* a highlight in the full transcript;
* a marker after the relevant sentence;
* an entry in an action-item list;
* the center of a focused conversation excerpt;
* a node in a structured meeting report.

These are different views of the same source fact.

A useful starting point is therefore to list the information already available independently of presentation:

```text
speaker turns
topic mentions
action items
policy flags
timestamps
named entities
```

Each item may become a span source.

Do not begin by asking how each item should be rendered. First determine what it says about the document.

## A span is more than its range

A span occupies a range of source offsets, but the span and the range are not the same thing.

```js
{
    start,
    end,
    data,
    origin
}
```

The range `[start, end)` is the geometry.

The span is an attributed entity that may carry:

* application data;
* provenance through its root `origin` or origins.

Two spans may occupy the same range while representing different facts:

```text
topic mention:   [-----------)
action item:     [-----------)
policy flag:     [-----------)
```

Their geometry is equal, but their meaning, data, and use in the resulting view are different.

Layer names, markers, and rendering hooks are pipeline concerns rather than properties of `SpanRecord`. This distinction becomes important as soon as spans are transformed. Expanding an action item to its containing speaker turn changes the geometry, but the resulting span can still record the root action item in `origin` when the chosen transformation preserves provenance.

## Separate root spans from derived spans

Many applications begin with spans produced outside HiText:

```text
transcriber       → speaker-turn spans
topic detector    → topic-mention spans
task extractor    → action-item spans
policy engine     → policy-flag spans
```

These are root spans: they report facts found directly by another system. Do not confuse them with a **Span Source**, the API term for an iterable or generator that supplies spans.

A view often needs additional geometry that no analyzer reports explicitly.

For a focused transcript review, the application may need:

```text
action item
    ├── containing speaker turn
    ├── surrounding context
    ├── end boundary
    └── omitted complement
```

These are derived spans.

They do not require rescanning the document. They follow from relationships already expressed by the root spans.

For example:

```js
spansCompose(
    spansFromLayer('action-items'),
    applyExpandTo('line', 1),
    applyMerge()
)
```

This does not discover new action items. It derives visible transcript context from the action items already generated by another layer.

The distinction is useful because source analysis and view construction evolve independently.

An analyzer answers:

> What is true about the document?

A HiText pipeline answers:

> Which further spans and representations should follow from those facts?

## Some spans are visible; others are analytical

Not every span needs rendering behavior.

Consider a compact transcript review:

```text
action-item spans
    → visible context spans
    → omitted spans
```

The action-item spans may be rendered as highlighted transcript text.

The omitted spans may be rendered as ellipses.

The visible context spans may render nothing at all. They exist only to calculate their complement.

```js
.addLayer(
    visibleSpans,
    null,
    'visible'
)
```

This is an analytical layer. It gives a name to an intermediate result without assigning visible output to it.

The distinction is important when designing a pipeline:

### Presentation spans

These directly affect the materialized result:

* speaker labels;
* highlighted topics;
* action-item markers;
* omissions;
* inserted labels.

### Analytical spans

These exist to support later computations:

* merged context windows;
* groups of related annotations;
* selected regions;
* boundaries extracted from larger spans;
* normalized or classified intermediate results.

Trying to make every layer visible usually mixes geometry with presentation and makes reuse harder.

A cleaner pipeline often computes several analytical layers before assigning any new output behavior.

## Derive geometry before choosing appearance

A common mistake is to combine geometry and presentation too early.

Suppose topic mentions should appear in short transcript excerpts. One procedural approach might be:

1. highlight the topic mentions;
2. render the entire transcript;
3. cut nearby speaker turns from the highlighted markup;
4. insert ellipses into the resulting HTML.

This makes the view depend on output that has already been materialized.

A span-oriented approach separates the stages:

```text
topic mentions
    → surrounding context
    → merged visible regions
    → omitted regions
    → omission rendering
```

The geometry is established first. Appearance is assigned only to the spans that participate in the final representation.

```js
const visible = spansCompose(
    spansFromLayer('topic-mentions'),
    applyExpandTo('line', 2),
    applyMerge()
);

const omitted = spansCompose(
    visible,
    applyInvert()
);
```

Only then does a layer decide how omitted spans should appear:

```js
.addLayer(
    omitted,
    spanHooksHide()
)
```

This ordering has two advantages.

First, the same geometry can be reused with different renderers or presentation policies.

Second, all operations continue to use the source coordinate space. No transformation needs to understand markup, terminal escape sequences, DOM nodes, or generated text.

## Recurring span patterns

Most HiText views can be decomposed into a small set of patterns. They are not rigid templates, but useful ways to recognize structure in a task.

### Independent annotation

Several systems describe the same source document without depending on one another.

```text
speakers ─────┐
topics ───────┼──→ materialized view
policy flags ─┘
```

Example:

```js
html()
    .addLayer(speakerSpans, speakerHooks)
    .addLayer(topicSpans, topicHooks)
    .addLayer(policyFlagSpans, policyFlagHooks);
```

Each source uses original document offsets. None of them emits output that another source must parse or preserve.

Use this pattern when several analyzers already know independently what parts of the document are relevant.

Typical applications include:

* speakers plus topic mentions;
* action items plus policy flags;
* diff markers plus code ownership;
* log severity plus correlated events;
* redaction plus explanatory annotations.

### Derivation

A new span set follows from an earlier one.

```text
A → B
```

Examples:

```text
action item → containing speaker turn
heading → heading text
match → context window
changed line → affected block
annotation → insertion point
```

In a pipeline, the earlier layer can be named and used as a source:

```js
spansFromLayer('action-items')
```

Derivation avoids repeating analysis and makes dependency explicit.

Use it when the new spans mean:

> Given these existing spans, construct another geometric or semantic view of them.

### Boundary extraction

A source span is collapsed to one of its boundaries:

```text
[----------)  →  |
```

For example:

```js
spansCompose(
    spansFromLayer('action-items'),
    applyCollapseTo('end')
)
```

The resulting point spans may insert:

* completion markers;
* assignee labels;
* due-date badges;
* generated references;
* line numbers;
* summary blocks.

A point span consumes no source content. It identifies a position where a layer may contribute generated output.

This pattern is preferable to manually calculating offsets in a separate pass because the boundary remains explicitly derived from its source span.

### Context expansion

A small important span determines a larger visible region:

```text
       [match)
    [context------)
```

Examples:

* speaker turns around a topic mention;
* nearby discussion around an action item;
* events near an incident;
* unchanged lines around a diff;
* neighbouring sentences around an extracted term.

```js
spansCompose(
    spansFromLayer('topic-mentions'),
    applyExpandTo('line', 2)
)
```

Context expansion answers:

> What larger region should remain understandable because this smaller region is important?

It often produces overlapping spans, which naturally leads to grouping or merging.

### Grouping and merging

Several nearby spans are represented by one enclosing region:

```text
[---)  [---)
    ↓
[----------)
```

For context windows:

```js
spansCompose(
    spansFromLayer('topic-mentions'),
    applyExpandTo('line', 2),
    applyMerge()
)
```

Without merging, nearby topic mentions may create repeated or overlapping excerpts. With merging, they become one continuous visible region.

The same pattern can group:

* related action items;
* clusters of log events;
* adjacent changes;
* nearby references;
* overlapping selections.

Sometimes the merged span is itself rendered. More often it is analytical input for another operation.

### Complement

A span set describing what should remain visible is inverted to describe everything outside it:

```text
document: [--------------------------------)
visible:          [--------------)
omitted:  [-------)              [---------)
```

```js
spansCompose(
    spansFromLayer('visible'),
    applyInvert()
)
```

This is one of the most useful projection patterns.

Instead of finding every region that should be hidden, define the interesting regions and derive their complement.

For empty-input and document-boundary behavior, see [`applyInvert()`](span-functions-reference.md#applyinvertexact).

Typical uses include:

* topic-focused transcripts;
* action-item reviews;
* code folding;
* focused logs;
* progressive detail;
* budget-limited context.

Complement spans commonly receive replacement or hiding hooks:

```js
.addLayer(
    omittedSpans,
    spanHooksHide()
)
```

### Aggregation

Several spans contribute to one generated result.

```text
A
B
C
 ↓
generated structure
```

Examples:

* headings become a table of contents;
* action items become a summary block;
* references become an appendix;
* links become collected definitions;
* events become a compact timeline summary.

Aggregation differs from merging.

Merging primarily combines geometry. Aggregation uses multiple spans and their data to construct another representation.

A custom generator can collect a completed named layer and emit one point span carrying both aggregate data and root origins:

```js
function spansFromActionItemSummary(
    _document,
    createSpan,
    { spansByName }
) {
    const items = spansByName['action-items'] ?? [];

    if (items.length === 0) {
        return;
    }

    const roots = items.flatMap(span =>
        Array.isArray(span.origin)
            ? span.origin
            : [span.origin ?? {
                start: span.start,
                end: span.end,
                data: span.data
            }]
    );

    createSpan(0, 0, {
        items: items.map(span => span.data)
    }, roots);
}
```

A layer can attach a replacement hook to this source and build one summary from `data.items`. The point span anchors that block at the start of the transcript; its origin array records the root items that contributed.

The resulting output is still anchored to the source document, even though its content is synthesized from several locations.

### Projection

A projection selects or reshapes the source representation while preserving the coordinate system of its annotations.

```text
source document
    + visible spans
    + omitted spans
    + generated content
    → derived view
```

Projection may involve:

* retaining only selected regions;
* replacing omissions with ellipses;
* inserting summaries;
* hiding details;
* showing different levels of context;
* moving derived information into another part of the output.

The source document itself remains unchanged. Reordering or restructuring is expressed by hiding original regions and generating their representation at selected boundaries.

This is what allows a compact transcript view to retain speaker labels, topic mentions, action items, and other independent annotations without translating their offsets.

### Target materialization

The same analytical span relationships may be used to configure pipelines for different output types:

```text
span pipeline
    ├── HTML
    ├── TTY
    ├── DOM
    ├── JSX
    └── custom structure
```

The analysis and derivation sources do not need to change merely because the output target changes. The renderer itself is selected when each pipeline is created, before target-specific hooks are attached; output values are produced later when `.render()` is called.

A root span does not contain HTML.

A context window does not contain terminal formatting.

An omitted region does not have to decide whether its ellipsis is a string, DOM node, JSX element, or structured record.

Those choices belong to materialization.

Use this separation when the same document view is needed in more than one environment, or when analysis should remain reusable independently of presentation.

## Build relationships, not rewriting procedures

The difference between the two approaches is easiest to see by comparing their shape.

A rewriting procedure might look like:

```text
highlight the source
→ locate action items in the modified output
→ cut unrelated turns
→ insert assignee markers
→ repair broken markup
```

Each operation consumes the result of the previous operation. Every step must understand what earlier steps produced.

A span pipeline instead describes relationships:

```text
speaker spans
action-item spans

action items
    ├── end boundaries
    │       └── assignee markers
    └── context windows
            └── visible regions
                    └── omitted complement

all spans
    → materialized view
```

The pipeline is still executable code, but its structure describes dependencies over one source document rather than a sequence of output rewrites.

This makes additions more local.

Adding topic highlighting does not require updating action-item extraction.

Changing omission rendering does not require recomputing context windows.

Changing from HTML to DOM does not require changing span generation.

## Keep one coordinate space

All these patterns compose because every span continues to refer to the same document.

Derived spans may change geometry:

```text
action item      [----)
expanded      [----------)
collapsed                  |
```

But their offsets still belong to the original source coordinate space.

Generated output has no effect on those offsets.

This gives the pipeline several useful properties:

* independent analyzers can be combined directly;
* derived layers can reuse earlier results;
* visible projections retain existing annotations;
* output formats can change without changing analysis;
* intermediate products remain inspectable;
* provenance can connect derived spans to their sources.

Once output positions become input positions, most of these properties disappear. Keeping materialization at the boundary preserves them.

## A practical decomposition method

When designing a HiText view, start with the following questions.

### 1. What facts already exist as spans?

Examples:

* speaker turns;
* topic mentions;
* action items;
* policy flags;
* timestamps;
* named entities.

These are usually produced by analyzers, parsers, matchers, or application state.

### 2. What additional geometry must be derived?

Examples:

* containing lines;
* surrounding context;
* merged windows;
* boundaries;
* complements;
* groups.

Do not decide presentation yet.

### 3. Which spans are only intermediate products?

Name them as analytical layers when later stages need to reuse them.

Examples:

* `visible`;
* `affected-lines`;
* `groups`;
* `selected-sections`.

### 4. Which spans directly affect output?

Assign hooks only to spans that need visible interpretation:

* highlights;
* omissions;
* markers;
* replacements;
* generated blocks.

### 5. Where should generated content be anchored?

Derive point spans from:

* document boundaries;
* line boundaries;
* span starts or ends;
* selected aggregate locations.

### 6. Which source regions should remain visible?

Often it is easier to define visible regions first and derive their complement than to enumerate everything that should be hidden.

### 7. What output representation is required?

Establish reusable analytical relationships first. Then choose HTML, TTY, DOM, JSX, or a custom renderer when configuring the pipeline and its target-specific hooks; materialization occurs later at `.render()`.

## One task, several decompositions

There is not always one correct span pipeline.

Consider a transcript excerpt centered on topic mentions.

One design might derive visible context directly from all topic mentions:

```text
topic mentions
    → expand
    → merge
    → invert
```

Another might first classify topics, then choose different context sizes:

```text
topic mentions
    → decisions   → larger context
    → names       → smaller context
    → combine
    → merge
    → invert
```

A third might combine topic mentions with action items before selecting context:

```text
topic mentions ─┐
                ├── relevant regions
action items ───┘
        → expand
        → merge
        → invert
```

The purpose of thinking in spans is not to force every task into one recipe. It is to expose the choices:

* which facts drive the view;
* how their geometry is transformed;
* which dependencies are shared;
* and where interpretation is attached.

## From patterns to API

Once the span relationships are clear, the API becomes a vocabulary for expressing them:

```text
use spans from an earlier layer
    → spansFromLayer()

expand into context
    → applyExpandTo()

combine overlapping regions
    → applyMerge()

extract a boundary
    → applyCollapseTo()

derive everything outside a selection
    → applyInvert()

compose the operations
    → spansCompose()
```

The function names are not the model. They implement the model.

The next guide introduces span sources and transformations through these relationships, then shows how to choose between built-in operations and a custom span generator.
